# ADR-004: Gameplay Ability System (GAS) for Abilities

## Status
✅ Accepted

## Context
The project needs a robust system for character abilities, attributes, effects, and progression. Options: custom system, Gameplay Ability System (GAS), or hybrid.

## Decision
Use Gameplay Ability System (GAS) as the foundation for all ability, attribute, and effect logic.

## Consequences

### Positive
- **Attributes**: Scalable, replicated, modifier stack (base + modifiers)
- **Gameplay Effects**: Instant, duration, infinite, periodic, executions
- **Abilities**: Activation, costs, cooldowns, tags, cancellation, prediction
- **Tags**: Hierarchical, query system (HasTag, HasAllTags, HasAnyTags)
- **Cues**: Decoupled VFX/SFX from logic, multicast, prediction
- **Prediction**: Client-side prediction with server reconciliation built-in
- **Replication**: Optimized, attribute-level, effect-level control
- **Editor Tools**: Ability Editor, Effect Editor, Tag Editor, Debugger
- **Extensibility**: Custom executions, calculations, tasks, cues

### Negative
- **Complexity**: Steep learning curve, many interconnected concepts
- **Boilerplate**: Significant setup (AttributeSet, ASC, Tags, Effects)
- **Debugging**: Can be opaque; requires Gameplay Debugger
- **Performance**: Overhead if misused (too many active effects, complex executions)
- **Version Lock**: Tied to UE version; API changes between versions

### Neutral
- **Custom System**: Could build simpler system, but would lack prediction, replication, tooling

## Alternatives Considered
- **Custom Ability System**: Full control, simpler for simple games, but no prediction/replication/tools
- **Hybrid**: GAS for complex (combat), custom for simple (movement) — adds inconsistency
- **Animation Montages Only**: Simple, but no cooldowns, costs, tags, replication
